01 how it works

Plan, review, apply. Nothing in between.

Adstack is a reconciler. Your configuration describes the campaigns you want; every plan reads the account, compares the two, and lists the operations that make them match. Changes made by hand show up in the next plan.

  1. step 1

    declare

    Campaigns, ad groups, keywords and ads in YAML. One file or a directory of them, reviewed in git.

  2. step 2

    validate

    Strict, offline checks. Unknown keys, bad match types and typo'd budgets fail with the exact location.

  3. step 3

    plan

    Reads the account and computes a pure, deterministic diff. Changes nothing. Save it with --out.

  4. step 4

    review

    Read every add, change and removal, plus the permissions applying it will need.

  5. step 5

    apply

    Re-verified against the live account, validated by the platform, then sent as one atomic request.

02 quick start

Try the whole loop without an ad account.

The sandbox is a local JSON account in .adstack/sandbox/. It applies the same API operations Adstack sends to Google and enforces the same request rules: atomic requests, temporary IDs created before they're referenced, one mutation per resource. It just doesn't serve ads or bill anyone.

Needs Python 3.11 or later. Omit [mcp] if you only want the CLI.

shell
$ pip install "adstack[mcp] @ git+https://github.com/markwroberts0/adstack" $ adstack init my-ads              # annotated starter configuration$ adstack validate my-ads          # offline checks$ adstack plan my-ads --sandbox    # what would change$ adstack apply my-ads --sandbox   # apply after typing 'yes'$ adstack plan my-ads --sandbox    # No changes.
against Google Adscredentials stay in your environment
$ export GOOGLE_ADS_CUSTOMER_ID=123-456-7890$ export GOOGLE_ADS_CLIENT_ID=… GOOGLE_ADS_CLIENT_SECRET=… GOOGLE_ADS_REFRESH_TOKEN=…$ adstack plan ads/ --out launch.plan.json$ adstack apply launch.plan.json

03 guardrails

It spends real money, so it's careful by default.

Every safety rule is enforced by the tool, not left to whoever runs it. Approving a plan is necessary but not sufficient.

New campaigns start paused

Nothing serves until you say so with --allow-enable.

Saved plans are re-verified

Applying a plan file recomputes it from the live account. If anything drifted since you reviewed it, the apply is refused.

Validated, then atomic

The request goes to Google with validateOnly first, then as one mutate with partialFailure=false. All or nothing.

Namespaced ownership

Only campaigns named adstack:<namespace>:… are read or changed. Everything else in the account is invisible to it.

Receipts for every apply

What changed and what the platform returned, written to .adstack/receipts/. Plan files and receipts are never overwritten.

No blind retries

If the network fails mid-mutate, the outcome is unknown. Adstack says so and stops, and the next plan shows what happened.

Spend needs an explicit flag.

Plans list the permissions they require. Applying without them fails, even with a reviewed plan file and --auto-approve.

flagneeded when
--allow-enablea paused campaign starts serving
--allow-budget-increasea budget or bid on an existing campaign or ad group increases
--allow-live-changesanything changes in a campaign that is serving now
  • Never deletes campaigns, ad groups, keywords or ads. destroy pauses.
  • Never adopts a campaign outside its namespace or converts one it doesn't understand.
  • Never silently changes something that isn't configured: it blocks the plan until you --prune.

04 ai assistants

Your assistant gets the same loop. Not the keys.

adstack mcp serves Adstack over the Model Context Protocol, so Claude and other clients can write a configuration, validate it and show you a plan. Applying is off unless you turn it on, and even then the server never relies on the model's judgment alone.

Claude Code
$ claude mcp add adstack -- adstack mcp --sandbox --root ./ads
toolsdrop --sandbox to plan against the real account
validateCheck a configuration offlineread-only
planCompute the changes; returns a plan_idread-only
show_planShow a plan the server createdread-only
stateList what Adstack managesread-only
reportPerformance and search terms, 7–30 daysread-only
example_configAnnotated example of every optionread-only
applyOnly with --sandbox or --allow-applywrites
  1. Off unless enabled. Without --sandbox or --allow-apply the server has no apply tool at all.
  2. Only reviewed plans. apply takes a plan_id from plan. The model can't submit arbitrary API operations.
  3. Account confirmation. The call must name the plan's account, so it's visible in the tool call your client shows you.
  4. Same permissions as the CLI. Enabling, raising spend and touching live campaigns each need their flag.
  5. Re-verified at apply time. If the account changed since you reviewed the plan, it's refused and the assistant must plan again.
  6. Contained. apply is annotated destructive so clients can always ask you first; paths outside --root are rejected.

05 ci

Ad changes go through pull requests.

Validate every pull request offline, plan against the account in a trusted workflow, and apply the reviewed plan file deliberately. plan --detailed-exitcode exits 2 when there are changes, and --json gives machines the same plan you read.

Planning against a real account needs credentials. Don't expose them to workflows that run untrusted pull request code.

.github/workflows/ads.yml
on: pull_requestpermissions:  contents: readjobs:  validate:    runs-on: ubuntu-latest    steps:      - uses: actions/checkout@v4      - uses: actions/setup-python@v5        with:          python-version: "3.13"      - run: pip install "adstack @ git+https://github.com/markwroberts0/adstack"      - run: adstack validate ads/

06 under the hood

No state file. Identity is the name.

Every campaign in the namespace is managed and every other campaign is ignored, so several configurations (or people) can share one account. Nothing to lock, nothing to lose.

adstack:<namespace>:<campaign id>Ad groups inside managed campaigns are named adstack:<ad group id>. It's a convention, not a lock: reserve the prefix for Adstack and don't rename managed campaigns by hand.

Bring your ad platform.

The workflow core knows nothing about Google Ads. A provider validates its slice of the configuration, reads the account and computes plans. Planning is pure: same input, same plan, no I/O. That's what lets saved plans be verified by recomputing them.

Ship a sandbox backend with your provider and tests for an initial plan, a no-op re-plan, drift, prune, destroy and the permission flags. No network in tests, ever.
